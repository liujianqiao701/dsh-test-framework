## §1 端清单

**端** = 业务上的"哪一头"。**默认端**是 `框架登记.json` 里 `ends[].default === true` 的那一个
（**默认端的模块名不带端前缀；非默认端必须带 `<端>-` 前缀**）。

**机器可读字段名（`框架登记.json` 的 `ends[]`，以这套为准）**：
`key`（端名）/ `default`（是否默认端）/ `menuCount`（端内顶级菜单数）/ `login`（怎么进这个端）/ `accounts`（该端账号）/ `note`。

| 端（`key`） | 是否默认端（`default`） | 端内模块数（`menuCount`） | 入口特征（`login`） | 账号（`accounts`） | 说明（`note`） |
| --- | --- | --- | --- | --- | --- |
| （待登记） | 是 / 否 | 0 | 如：同一登录页换账号即进入；或独立 URL（带参数的 H5） | 如：`ljq`（中心端）/ `ljq1`、`ljq4`（成员端） | 如：默认端 → 模块名不带端前缀 |

> **必须实地核**：端不是需求文档里的一章。**在环境里确认有哪些端、各自怎么进**（同一登录页换账号？独立域名？带参数的 H5？），
> 找不到就**问用户**。端清单一旦定下，模块命名规则就跟着定了。
>
> ⚠️ **端自己也可以就是一个模块**（例外）：整端不拆模块时（如患者端只有一个 H5 承载多个业务对象），
> 在 `modules[]` 里给它建**一个**模块、`end` 写它自己（如 `患者端`），业务对象用 `businessObjects` 表达；
> 关联边的 `from` / `to` **可以直接写端名**（校验器把端名当合法链路节点，不报"模块缺失"）。

## §3 关联边表

一条边 = 一次**跨模块交接**。**两端都要登记**：这里出现 `A → B`，就必须也出现 `B → A`
（只写一边 = **单向边**，`test_framework_link` 会报 `E_ONE_WAY`，闸门 `linksChecked` 不通过）。

| id | 链路 | from → to | 关联类型 | 业务对象 | 交接点 | 共享表 | 两端路由 | 名字差异 | 联测账号 | 依据 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| （待登记） | | | 审批流 / 上游依赖 / 同源同物 / 数据同源 / 关联 | | 哪个环节把活交给对端 | `schema.table`，多个用 `<br>` 分隔 | `from: /xxx`<br>`to: /yyy` | 两端叫法不同就写这儿 | 联测要用的账号（指到 `环境与账密.md`） | 需求文档名 §章节 | 已确认 / 待核 |

**列怎么填**：

| 列 | 要求 | 不许做的事 |
| --- | --- | --- |
| `id` | 稳定标识，插件按 `from\|to\|业务对象` 哈希生成（`R-xxxx`） | 别手工改（改了下一次登记会对不上） |
| `链路` | 这条边属于哪条业务链（配 `框架登记.json` 的 `flows[]`） | 留空 ❌（没链路就没法判"链路断点"） |
| `from → to` | **模块目录名**（`A → B`），两端各写一条 | 写成菜单名 / 表名 ❌ |
| `关联类型` | 审批流 / 上游依赖 / 同源同物 / 数据同源 / 关联 | 编新类型 ❌（要加先更新本文件说明） |
| `交接点` | **哪个环节把活交给对端**（如"成员端审批通过后提交中心端受理办结"） | 写"有交互" ❌ |
| `共享表` | 两端**真的都读写**的表，写全 `schema.table` | 把"看起来相关"的表都堆上 ❌ |
| `两端路由` | `from` / `to` 各自的页面路由 | 写完整 URL ❌（环境会换，路由不会） |
| `名字差异` | 同一件事两端叫法不同时写清（如 成员端「短缺登记」/ 中心端「短缺药品」） | 留空 → 跨端核对时必然误判 |
| `联测账号` | 跨端联测要用的账号，**只写账号名，密码指向 `环境与账密.md`** | **把密码写在这里** ❌（凭据只有一处出处） |
| `依据` | 需求原文**文件名 + 章节号**（跨端逻辑写在哪儿） | 拿猜测当依据 ❌ |
| `状态` | 已确认 / 待核 | 没核过就写"已确认" ❌ |

**机器可读字段名（`框架登记.json` 的 `relations[]`，以这套为准）**：

| 本表列 | `relations[]` 规范字段 | 说明 |
| --- | --- | --- |
| `id` | `id` | `R-xxxx` |
| `链路` | `flow` | 链路名 |
| `from → to` | `from` / `to` | 模块目录名（**也可以是端名**，见 §1 例外） |
| `关联类型` | `kind` | |
| `业务对象` | `businessObject` | 跨端对齐的抓手 |
| `交接点` | `handoff` | |
| `共享表` | **`tables`**（字符串，多个用 `<br>`，可带反引号） | 插件同时写兼容别名 `sharedTables[]` |
| `两端路由` | **`fromRoute`** / **`toRoute`**（字符串） | 插件同时写兼容别名 `routes{from,to}` |
| `名字差异`+`依据`+`状态` | **`note`**（字符串） | **人写的自由文本**：插件写的边**只在显式给 `note` 时才落这个键**（**绝不拿那三个字段拼**——机器拼的散文会被后续会话当成"人确认过的口径"）；缺位时模块 `SKILL.md` 的说明列渲染 `[自动] …` 兜底串，那个**只进 markdown、不进 JSON**。兼容别名 `nameVariance` / `evidence` / `status` 照旧落 |
| `状态` | `registeredOnBothSides` | **自动算**：两端都登记了反向边才 `true` |

> **两套字段名都认**：规范名（`tables` / `fromRoute` / `toRoute` / `note`）与插件原名（`sharedTables` / `routes` / `nameVariance` …）
> **读的时候两种都吃**；**写的时候两套都写**（规范名为主，原名为兼容别名）——
> 所以无论是产品侧脚本还是插件写出来的，两边读哪套都能读到。**规范名没值时不写这个键**（不留空壳字段）；
> `note` / `fromRoute` / `toRoute` / `tables` 已有值时，**重复登记不会覆盖**（本次没给就沿用旧值）。
>
> 手写时**照规范名写**：`flows[]` 的节点用 **`nodes[]`**（不是 `order`）、端的名字用 **`ends[].key`**（不是 `name`）。

## §6 维护规则

1. **两端都要登记**：只在 A 端登记 `links` = 单向边。A 端登记完，**对端模块也要登记它那一条**。
2. **怎么登记**：`test_framework_module_add` 传 `end` / `businessObjects` / `links`
   （`links: ["对端模块名"]` 是最简写法）—— 它会写 `框架登记.json` 的 `relations[]`，
   并往模块 `SKILL.md` 的「§关联模块」段**追加**一行（**只追加，绝不覆盖**）。
3. **改完必复核**：`test_framework_link`（只在读，不改文件）。它查：
   关联边两端模块是否存在 / 单向边 / 链路断点 / 端前缀命名 / 非默认端没写业务对象 / 路由漂移 / 模块登记落点缺失。
   **错误没清零就别开工**（闸门 `linksChecked` 认的就是这几条；warning 不拦人但值得看一眼）。
4. **本文件是唯一事实源**：模块 `SKILL.md` 的「§关联模块」段只写本端视角，
   **不要把本文件的内容抄进模块**（抄了必然两边不一致）。
5. **改了路由 / 菜单 / 模块名 → 回头改本文件**：否则 `test_framework_link` 会报 `W_ROUTE_DRIFT`，
   跨端核对时按旧路由去找必然找不到。
6. **没有关联就写「暂无」**：一个模块确实不与任何模块关联时，
   在它的 `SKILL.md`「§关联模块」表里写「暂无」（**不要留「待登记」** —— 那分不清"没有"和"没查"）。
