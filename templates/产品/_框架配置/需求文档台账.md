## §0 为什么要有这本台账

需求文档的路径**不区分版本**，一份文档又常常**包含多个子模块**，还有的**逻辑写在另一份文档里**。
这三件事决定了「直接打开文档开始测」几乎一定出错。台账就是把这三件事**固化下来**：

| 问题 | 只靠记忆会怎样 | 台账怎么解决 |
| --- | --- | --- |
| **这份文档是哪一版？** | 拿旧版当新版测，测完全白干 | 记 `版本` 列（判定方法见 §4） |
| **一份文档里有几个模块？** | 当成一个模块测，报告错位、覆盖不全 | 命中拆分判据（§2）就必须先停下来问用户 |
| **A 文档的逻辑写在 B 文档里** | 按 A 的描述提缺陷，结果 B 里早就写明了口径 | §3 固定问「还关联了哪些文档」，答案落 `关联的其它需求文档` 列 |
| **文档里划掉的部分** | 拿已取消的需求去提缺陷 | §5 划掉项单独出核对表，回头核环境 |

> ⚠️ **本文件可被机器回填**：插件会**追加一行或覆盖某几行**。
> **不要改动表头列名与列顺序**，**不要在表格中间插入说明性文字行**（说明写在表格下方）。
> ⚠️ 路径一律写**本地绝对路径**；凭据（文档打开密码）**不写在本文件**，见《环境与账密.md》§5。

## §2 拆分判定与处置（**强制拆分判据**）

### 2.1 强制拆分判据（命中**任一**就要停下来问用户，**不许自己拆**）

| # | 判据 | 怎么看 | 为什么它意味着要拆 |
| --- | --- | --- | --- |
| **A** | **页数 > 100 页** | 抽取后正文页数 | 100 页以上几乎不可能是一个叶子菜单的事，硬当一个模块测必然覆盖不全 |
| **B** | 一级章节 / 「修改点」里出现 **≥2 个不同业务功能名** | 通读目录 + 「修改点」小节标题 | 两件功能各有自己的页面与数据流，测法完全不同 |
| **C** | 出现 **≥2 个不同的叶子菜单名**（含同一父菜单下的多个子项） | 文档里出现的系统菜单名，与《模块路由.md》§1 的**模块**列对照 | **一个模块 = 一个叶子菜单**（本框架的定义），两个叶子菜单就是两个模块 |
| **D** | 用户描述里出现**并列词**（「包含 / 以及 / 和 / 里面还有」）且指向**多个功能** | 用户原话 | 用户已经在用一句话描述多件事了，别替他合并 |

> 判据 B / D 需要**读一遍**才能判 —— **不许只看文件名**就下「不用拆」的结论。

### 2.2 范例（照这个尺度判）

> 需求文档 `药品联动保障` 里同时写了 **`缺药登记`**、**`短缺评估`**、**`余缺调拨`** 三件事。
> - 命中判据 B（三个业务功能名）、判据 C（三个不同的叶子菜单 / 功能入口）。
> - **结论：必须拆成 3 个模块** —— 每个模块各自一份 `SKILL.md`，各自一套
>   `requirement\` / `final\` / `report\` / `data\`，各自出各自的冒泡测试报告。
> - ❌ 错误做法：建成一个 `药品联动保障\` 模块，把三件事塞在一份报告里。

### 2.3 处置：**用 `ask_user_question` 把方案摆给用户确认**（确认后才动手）

命中判据后，**不要**直接开始建目录。固定这么问：

```
问：这份需求文档看着包含多个模块，我建议这样拆，你确认吗？
   建议拆分方案：
     ① <模块名> —— 依据：<一级章节号 / 页数区间 / 修改点编号>
     ② <模块名> —— 依据：<...>
     ③ <模块名> —— 依据：<...>
   合并方案（不拆）会怎样：<说清代价，如「覆盖不全 / 报告错位 / 无法独立归档」>
选项：A 按建议拆（推荐） / B 我指定别的拆法 / C 不拆，按一个模块测
```

| 用户回什么 | 你怎么做 |
| --- | --- |
| 确认按建议拆 | 建 N 个模块目录 → 每个复制模块骨架 `SKILL.md` → 回填 §1 的 `拆分出的模块` → 在《模块路由.md》§1 各登记一行 |
| 给出别的拆法 | **照用户的拆**，把「按用户的什么话拆的」写进 §1 `备注` |
| 说「不拆」 | 照做，但**必须**在 §1 `备注` 记「用户明确不拆，依据：<原话>」，并在报告里写清覆盖范围的局限 |
| **不答** | **停**，等答复；不许自己拍板 |

## §3 跨文档关联确认（**必问**）

**为什么要问**：A 文档里某个逻辑**其实是在另一份需求文档里定义的** ——
只按 A 的描述去测，会把「B 里写明的既有口径」当成缺陷提出来，白跑一趟还惹人。

**固定问法**（每登一份文档问一次，答完落 §1 的「关联的其它需求文档（本地路径）」列）：

```
问：这份《<文档名>》要和别的需求文档一起看吗？比如它依赖某份文档里已经定好的表结构、
   枚举值、接口口径或上下游流程？
选项：A 有关联（请给文档名或关键词，我去定位绝对路径） / B 没有关联 / C 不确定，你帮我找
```

| 用户回什么 | 你怎么做 |
| --- | --- |
| 给了文档名 / 关键词 | 用 `find_req_doc.py --query "<关键词>" --system <系统>` **定位并写本地绝对路径**，**不许写模糊描述**，也不许凭记忆填路径 |
| 说没有 | `关联的其它需求文档` 列写 `无`（**写「无」，不要留空** —— 留空分不清「问过没有」和「没问」） |
| 说「你帮我找」 | 按文档里出现的表名 / 枚举 / 接口名反查同系统目录下的候选，**列给用户确认后再落表** |
| 不答 | **停**，等答复 |

> 多份关联文档用 `；` 分隔；每条都必须是**能直接打开的绝对路径**。
> 后续读需求时，**先读关联文档再读本文档**，口径以关联文档为准。

## §4 版本确认（**必问**）

**为什么要问**：需求文档路径**不随版本变** —— 新旧版本放在**同一个目录**，用前不确认版本，后面全白干。

**固定问法**：

```
问：本次测的是哪一版？（我从 <依据> 看像是 <版本号>，确认一下）
选项：A <版本号>（推荐） / B 别的版本（请给版本号） / C 我去查
```

### 4.1 判据提示（按顺序看）

| # | 看什么 | 怎么判 |
| --- | --- | --- |
| ① | `各版本升级清单\` | **最新版本号以它为准** |
| ② | 顶层**无版本号**文档 vs **`2606betaN版本需求方案\`** 子目录 | 顶层 = 主线；`2606betaN版本需求方案\` 子目录 = **该批次冻结子集 / 下个迭代增量** |
| ③ | `各版本方案备份\` | **是历史备份，别当最新** |
| ④ | 以上都不确定 | **问用户**（版本判错，后面全白干） |

### 4.2 ⚠️ 警告：**不许用文件时间判断版本**

实测过：**备份目录里的文档 mtime 可能比主线更新**（同一天批量改动会导致 mtime 完全不可信）。
用时间判版本 = 直接把「最新」判成「历史备份」。判版本只认 **①目录位置 ②版本号字样 ③用户确认**。

**用户不答怎么办**：**停**，等答复。这一项**没有可以自己拍板的余地**。

## §5 划掉项（删除线 / 修订删除 = 已取消）

| 规矩 | 内容 |
| --- | --- |
| **不当需求读** | 文档里**删除线 / 修订删除 = 需求已取消**。**不许**拿划掉的内容当「应该有的功能」去提缺陷 |
| **但必须回头核** | 划掉的项要**单独出「取消项核对表」**，逐项到**测试环境**确认系统里是不是也去掉了 |
| 环境结论 → 动作 | `已同步取消` = 合规，不提单；**`未取消（残留）` = 提缺陷**；`无法判定` = 写明缺什么，**不许含糊成通过** |

- 覆盖种类：`w:strike`（单删除线）、`w:dstrike`（双删除线）、段落 / 样式层删除线、`w:del` 修订删除 —— **四种都要覆盖**。
- **整段、整张表被划掉也算取消**（实测抓到过整张表被划掉的例子）。
- 产物：`<模块>\report\<模块>-取消项核对-<yyyyMMdd>.md`（逐项表 + 未取消清单 + 证据路径）。
- 本台账里对应的字段：`框架登记.json` 的 `documents[].cancelledItemCheck`
  （`未做` / `已同步取消` / `未取消(残留)` / `无法判定`）。

**核对通道**（按「这功能在哪儿」选，别只挑一个）：

| 功能在哪 | 用什么 |
| --- | --- |
| 页面 | playwright MCP（用户要看着操作时**必须**用） |
| 接口 | `keyword_mcp` 报文落盘 |
| 库 | 只读 SQL；**整表 / 整列被划掉时，最省的判据是查 `information_schema`** |
