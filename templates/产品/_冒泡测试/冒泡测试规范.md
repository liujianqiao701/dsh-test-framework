# 冒泡测试规范（按模块）

> 适用产品：**本框架下的任意产品** ｜ 触发词：**「测试 <产品名> 的冒泡测试」**
> 本规范是**产品级共享规范**（不是框架级 skill），由 `AGENTS.md` §三 路由。
> 配套文件都在本目录：`archive_reports.py`（**报告回收**，满 24h 自动归档）、`bubble_db.py`（数据库预检/核对）。

---

## §0 组织原则：一个模块 = 一个顶级菜单 = 一份独立报告

冒泡测试**按模块拆分**，不出一份全局大报告。理由：

| 场景 | 按模块的好处 |
| --- | --- |
| 新增一个模块 | 直接建模块文件夹，冒泡测试独立跑，不牵扯别的模块 |
| 老模块迭代新功能（模块名没大改） | **还是这个模块**，新一轮出一份**独立报告**，上一轮的历史自动归档，不会被覆盖 |
| 出了缺陷要跟进 | 报告和证据都跟着模块走，模块负责人只翻自己那个文件夹 |

**模块 ↔ 系统菜单**：本框架说的"模块"= **系统里的一个顶级菜单**（如"药品管理""统计报表""系统设置"）。
菜单与模块文件夹的对应关系记在各模块 `SKILL.md` 的 §1 定位；对不上时以**系统实际菜单**为准并回头补 §1。

**开工前先读该模块的两份 skill**（模块规范已按版本拆开，**不要拿别的版本的规范来测这一版**）：

| 读什么 | 作用 |
| --- | --- |
| `<模块>\SKILL.md` | **索引** —— 模块定位 / 公共约定 / **§8 版本索引**（哪个版本对应哪份规范） |
| `<模块>\skill\<本次版本>\SKILL.md` | **该版本的规范** —— §V2 本版需求范围 / §V3 本版测试要点 / **§V4 本版造数逻辑** / §V5 本版坑 |

**产物一律落模块自己的目录**：

| 产物 | 落位 |
| --- | --- |
| 冒泡测试报告 | `<模块>\report\冒泡测试-<模块>-<yyyyMMdd>[-批次N].md` |
| 截图 / 接口报文 / 遍历清单 / SQL 结果 | `<模块>\data\冒泡测试-<yyyyMMdd>\` |

> 报告与证据满 **24 小时**自动归档到 `_archive\报告归档\<模块>\<yyyyMMdd>\`（见 §11）。
> 所以模块的 `report\` 里**只会看到最近 24 小时**的报告，历史都在归档区。

## §1 第一步：向用户索取信息（必须问，问全再动手）

| # | 要什么 | 为什么必须要 | 用户不答怎么办 |
| --- | --- | --- | --- |
| 1 | **测试环境地址**（IP/域名 + 端口） | 每次以用户当次给出的为准 | **停**，等答复 |
| 2 | **账号 + 密码** | 规范要求每次问 | **停**，等答复 |
| 3 | **数据库地址**（host / port / 库名 / 用户名 / 密码 / schema） | §7 数据核对要连 | **停**，等答复 |
| 4 | **本次测哪个模块**（或"全部"） | 决定报告出几份、落哪里 | 列出模块清单让他选 |
| 5 | **破坏性按钮是否允许点**（删除/审核/发布/下发/停用/导入） | 点了会改真实数据 | 默认**只对自造数据点** |
| 6 | 本次时间窗 | 决定要不要分批 | 默认**能跑多久跑多久，跑不完留断点** |

- 第 4 项答"全部"→ 按 §3 枚举模块清单**逐个跑**，**每个模块各出一份报告**（不要合并成一份）。
- 第 5 项是安全闸：用户说"每个按钮都要点"通常指**功能要覆盖到**，不是"把生产数据删了"。
  遇到破坏性按钮一律**先自己造一条数据再操作它**。若用户明确要求用真实数据点，**先让他书面确认**。

## §2 第二步：环境预检（不通过就停，不要硬着头皮往下走）

```powershell
# 数据库预检 + 行数基线（基线落当前模块的 data 目录）
python bubble_db.py precheck --host <DB_HOST> --port <DB_PORT> --dbname <DB> `
       --user <USER> --password <PWD> --schema <SCHEMA> --out "<模块>\data\冒泡测试-<yyyyMMdd>\baseline.json"
```

| 检查项 | 怎么查 | 不通过的处置 |
| --- | --- | --- |
| 页面可达 | 打开登录页，看 HTTP 状态 + 标题 | 停，报"环境不可达" |
| 页面版本 | 页面上的软件版本号 | **记进报告**（没版本号的问题单没法复现） |
| 登录成功 | 用用户给的账密登录 | 账密错 → 找用户；登录报错 → 按 §8 记录 |
| **模块 ↔ 菜单** | 在左侧菜单里找到本次要测的模块，确认菜单路径 | 找不到 → 问用户模块在哪个菜单下 |
| 接口基线 | 挑一个业务接口，看状态码与耗时 | 接口 5xx → 停，环境有问题 |
| 数据库可达 | `select version()` + schema 列表 | 连不上 → 问用户要正确地址，**不要自己猜** |
| 关键表基线 | 相关表 `count(*)` 快照 | 存成基线，§7 对账用 |

**预检结论表**（写进报告开头）：

```
环境：<地址>  版本：<版本号>  账号：<账号>（<角色/机构>）
本次模块：<模块名>（系统菜单：<顶级菜单> / <二级菜单>）
预检：页面 ✅ / 登录 ✅ / 接口 ✅ / 数据库 ✅ / 权限：本模块可见 N 个页面
基线：<关键表>共 N 行（详见 data\冒泡测试-<日期>\baseline.json）
```

## §3 第三步：先建遍历清单，再执行（这是能不能测完的关键）

**不要**边点边想。先把本模块"要测什么"枚举成清单，落成文件，再逐条打勾。

### 3.0 工具选型（先定这个，再枚举）

| 场景 | 用什么 | 为什么 |
| --- | --- | --- |
| **用户要「看着页面操作流程」** | **playwright MCP**（`mcp__playwright__browser_*`）**有头浏览器 + 真实操作** | 用户要肉眼看着过程，**必须真开浏览器真点**（`AGENTS.md` 铁律 10） |
| 复杂/自绘控件点不动 | **playwright MCP** 真实点击 | 实测 uni-app 自绘组件 `kw_click` 点不动（Timeout 30000ms），playwright 可以直接点动 |
| 接口报文取证 / toast 历史 | `keyword_mcp`（`kw_expect_response` / `kw_get_toast`） | 自动落盘、免自己 hook XHR |
| **看这一屏长什么样 / UI 还原度** | **截图 + `read_image` 自己读**（模型原生视觉，秒级） | 错位、遮挡、截断、颜色、图标**DOM 里全是"正常"**，只有图能证明（`AGENTS.md` §三「看图识图」，**不读图 = 漏检**） |
| 小视口老内核兼容性 | `cr69_mcp`（Chromium 69） | ⚠️ ES module 构建的页面在它里面 `#app` 全白，**跑不起来就换 playwright** |

> 冒泡测试默认也**优先 playwright MCP 执行**（真实点击 + `browser_snapshot` 取数 + `browser_console_messages`
> 看报错），**每走完一屏截图后用 `read_image` 读一遍**（别只存档），**接口报文另用 kw 补取证**。
> 改用哪个工具、为什么改，**写进报告的"工具层说明"**。
> ⚠️ **图只能用来说"长什么样"**：报告里的**数值/金额/编码/单号/图表数值**必须回 DOM / 接口报文 / SQL（读图会读数）。

### 3.1 定位本模块的页面清单
在左侧菜单里展开**本模块**（顶级菜单）+ 其下所有二级/三级菜单，得到 `菜单路径 → URL`。

```javascript
// 把菜单树整棵捞出来（按实际 DOM 调整选择器）；记得逐级展开才能拿到折叠项
JSON.stringify([...document.querySelectorAll('.el-menu .el-submenu__title, .el-menu .el-menu-item, aside a')]
  .map(e => ({ text: e.innerText.trim(), href: e.getAttribute('href') || '' })).filter(x => x.text))
```

### 3.2 每个页面枚举"可操作元素"
进入页面后枚举四类：**tab / 列表 / 按钮 / 输入项**。
按钮要记 **文字 + 选择器**（文字重复时用 nth 区分）。

### 3.3 每个页面枚举"接口"
进入页面时开启网络监听，收集本页全部 XHR/fetch：`URL + method + 状态码 + 耗时 + 业务 code`。
**接口清单是 §4.4 的核对依据** —— 接口报错往往页面不报错，只看页面会漏。

### 3.4 落成本模块的进度文件（断点续测的基础）

```
<模块>\data\冒泡测试-<yyyyMMdd>\遍历清单.json
```

```json
{
  "module": "<模块名>", "env": "<环境名>", "version": "<页面上的版本号>", "account": "<账号>",
  "started": "2026-09-21T13:00:00",
  "pages": [
    {"menu": "<顶级菜单> / <二级菜单>", "url": "/<路由>", "status": "done",
     "tabs": [{"name": "<页签名>", "status": "done"}],
     "lists": [{"name": "<列表名>", "status": "done"}],
     "apis": [{"url": "/api/drug/list", "status": 200, "code": 0}],
     "buttons": [{"text": "查询", "status": "done"}, {"text": "导出", "status": "failed", "issue": "MAOPAO-003"}]},
    {"menu": "<顶级菜单> / <二级菜单2>", "url": "/<路由2>", "status": "pending"}
  ]
}
```

`status`：`pending` / `done` / `failed`（指向 issue 编号） / `blocked` / `skipped`（无权限等）。

> **中断了就靠它续测**：下次从第一个非 `done` 节点接着跑。跑不完时报告里写清"本批次覆盖 X/Y 个页面"。

## §4 第四步：逐层执行（每个页面按 1→5 顺序）

### 4.1 打开页面
记录：加载是否成功、耗时、**console 报错**、失败的静态资源（404 的 js/css/图片也算问题）。

```
mcp__playwright__browser_navigate url=<页面地址>      # 真实浏览器打开（用户要看着时用这个）
mcp__playwright__browser_console_messages level=error # 控制台报错
mcp__playwright__browser_network_requests static=true # 含静态资源的失败项
```

> ⚠️ **用户说"我看着你操作"时，这一节的每一步都必须真的在浏览器里发生** ——
> 不许改成只读 DOM、只抓报文或跑脚本代替（`AGENTS.md` 铁律 10）。每步先说要做什么、预期是什么，再执行。

### 4.2 逐个切 tab
每个 tab 都点开：内容是否渲染、有没有报错、tab 之间数据是否串。

### 4.3 每个列表走一遍（**列表是问题高发区**）

| 动作 | 要点 |
| --- | --- |
| 默认加载 | 是否有数据、列是否错位、表头与数据是否对得上 |
| 分页 | 首页 / 下一页 / 末页 / 跳页 / 改每页条数（20→50→100） |
| 排序 | **每一列都点一次**（升/降），看是否真生效、是否报错 |
| 查询 | 精确 / 模糊 / 空结果 / 超长文本 / 特殊字符（`%` `_` `'` `<>`） |
| 重置 | 重置后条件是否真的清空 |
| 导出（若有） | 能否导出、文件是否为空、行数与列表是否一致 |
| 空数据 | 用查不到的条件，看空态展示（不是白屏/报错） |

### 4.4 对照接口清单
逐个核对：**状态码 200？业务 code 0？返回条数与列表一致？**
接口报错即使页面没提示，**也算缺陷**（静默失败，用户会以为没数据）。

### 4.5 逐个点按钮

| 类型 | 例子 | 怎么点 |
| --- | --- | --- |
| 安全类 | 查询 / 重置 / 展开 / 详情 / 返回 / 关闭 | 直接点 |
| 只读类 | 导出 / 打印 / 预览 | 直接点，核对产物 |
| **破坏性类** | 新增 / 编辑 / 删除 / 提交 / 审核 / 发布 / 下发 / 停用 / 导入 | **先造测试数据再点**（见 §6） |

**每个按钮点完立刻三问**：① 页面报错了吗？② 接口报错了吗？③ 卡住了吗？
任一命中 → 立刻按 §8 记录（趁现场还在，先截图再继续）。

## §5 第五步：模拟用户做增删改查

| 操作 | 必须覆盖的场景 |
| --- | --- |
| **查** | 单条件 / 多条件组合 / 时间区间 / 空结果 / 分页边界 |
| **增** | ① 必填留空 → 应有校验提示 ② 超长输入 → 应截断或报错 ③ 特殊字符 → 不应报 500 ④ **重复提交**（连点两次保存）⑤ 正常新增一条并**记下主键** |
| **改** | ① 打开编辑看**回显是否正确**（加密字段、日期、下拉回显是高发区）② 改一个字段保存 ③ 页面与**数据库都核对** |
| **删** | ① 删除确认弹窗是否正常 ② 删自造数据 ③ 删后列表与**数据库都核对** |

**每一步记三样**：`做了什么操作` → `页面结果` → `数据库结果`。

## §6 数据策略（保证"点了破坏性按钮"不出事）

1. **只碰自造数据**：对任何"会改数据"的按钮，先造一条自己的数据再操作它；真实业务数据**不动**。
2. **造数也要动态**：造数前先读数据库真实数据，据此算不重复的主键/编码 —— **禁止写死**
   （思路：先侦数、再算新键、再回查确认不存在；通用规则见 `skills\db-seeding\SKILL.md` §4）。
   - **权威出处**：框架级 skill **`db-seeding`** §4 —— 连库/造数的通用规则（自动加载）。
   - **造数前先查"本次版本"的造数逻辑**（模块规范已按版本拆开，顺序别搞反）：
     **① 本版规范** `<模块>\skill\<本次版本>\SKILL.md` **§V4** →
     **② 模块索引** `<模块>\SKILL.md` **§8 版本索引**（看哪条对应本次版本）→
     **③ 模块** `final\` / `scripts\` → **④** `_archive\scripts\`。
     四处都没有才算"没有"（如某模块的 `final\<版本>-<模块>造数逻辑.md`、`_archive\scripts\` 里的 `gen_*` 脚本）。
     **有就照做，不要重新编**；确实没有才问用户。
     **拿到新造数逻辑后落 `<模块>\final\<版本>-<模块>造数逻辑.md`，并回填该版规范 §V4 + 索引 §8**（多版本并存不覆盖）。
   - 主键用 `skills\db-seeding\scripts\next_key.py` 算（按**数值最大**，文本序会把 `99999` 当最大，骗人）。
3. **自造数据必须打标**：名称/备注/编码带统一标记，例如 `冒泡测试_<日期>_<序号>`、编码前缀 `MAOPAO`。
   好处：一眼认出、收尾一条 SQL 捞出、万一漏清用户也能识别。
4. **收尾清理**：按主键逐条删除（不要宽泛条件 DELETE），删完**核对行数回到基线**，并写进报告"是否已还原"。

## §7 第六步：连数据库核对（用户给的地址）

| 核对 | 做法 |
| --- | --- |
| **列表 ↔ 表** | 列表"共 N 条"、实际渲染 M 条，都跟 `select count(*)` 对 |
| **详情 ↔ 行** | 页面详情字段逐个与库里对应列比对（**加密字段不能直接比密文**） |
| **操作 ↔ 变化** | 增/删/改前后的行数与内容变化必须等于预期 |

```powershell
python bubble_db.py query --host <H> --port <P> --dbname <DB> --user <U> --password <PWD> `
       --schema <SCHEMA> --sql "select count(*) from <SCHEMA>.<表名>"
```

**原则：以 SELECT 为主**（`query` 子命令已强制只允许 SELECT）。只有清理自造数据时才 DELETE 且必须按主键
（用 `bubble_db.py cleanup`）。报告里**附上实际执行的 SQL 与结果**，否则对账不可复现。

## §8 第七步：问题记录规范（**本规范的核心，必须逐字执行**）

### 8.1 每条问题必须填满这些字段

| 字段 | 必填 | 说明 | 反例（不许这样写） |
| --- | --- | --- | --- |
| 编号 | ✅ | `MAOPAO-001` 顺序编号（模块内独立编号） | —— |
| 级别 | ✅ | **阻塞** / 严重 / 一般 / 建议 | —— |
| **模块** | ✅ | 本次测的模块（= 顶级菜单） | "系统" ❌ |
| **页面** | ✅ | 菜单全路径 + URL | "药品页面" ❌ |
| **区域** | ✅ | 哪个 tab / 哪个列表 / 哪个表单 | "列表那里" ❌ |
| **对象** | ✅ | 按钮文字 或 字段 label（附定位选择器） | "一个按钮" ❌ |
| **操作** | ✅ | 点了什么、填了什么值（原样） | "操作后" ❌ |
| **需求原文依据** | ✅ | **文档名 + 章节号 + 原文引用**（需求确实没写的写 `需求未明确`） | 猜、或者干脆不写 ❌ |
| **与需求不符点** | ✅ | 单独一行点明差在哪个**字段 / 分支 / 文案 / 口径** | "跟需求不一致" ❌ |
| 现象 | ✅ | 页面报错原文 / 接口状态码+响应体 / 阻塞表现 | "报错了" ❌ |
| 证据 | ✅ | 截图路径 + 接口请求响应 + console 原文（**正文只写路径，长报文不进正文**） | "截图见附件" ❌ |
| 依据通道 | ✅ | 这条结论靠什么定的：DOM / 接口报文 / SQL / 截图 | —— |
| 影响 | ✅ | 是否**阻塞后续**、影响哪些功能 | —— |
| 复现 | ✅ | 必现 / 偶现（几次中几次） | —— |
| 时间 | ✅ | 精确到分 | —— |

> ⚠️ **2026-10-13 加的两条 + 一条排版硬要求**（用户要求"缺陷要一目了然、不要密密麻麻一大长篇"）：
> ① **每条缺陷必须有「需求原文依据」**（文档名+章节号+原文引用）与**「与需求不符点」** ——
> **不许拿猜测当依据，也不许因为找不到依据就不写这条**（找不到就写 `需求未明确`）；
> ② **复现步骤必须清晰可照做**：`1. 2. 3.` 每步一行（打开什么 → 输入点什么 → 看到什么）；
> ③ **一条缺陷一小节、每条 ≤ 20 行**，禁止把多条揉成一大段。

### 8.2 阻塞类问题单独置顶

**阻塞定义**（命中任一即为阻塞，必须置顶并决定是否停测）：
- 页面白屏 / 一直 loading 不结束
- 接口超时、5xx、或业务 code 异常导致流程走不下去
- 弹窗/遮罩关不掉，必须刷新才能继续
- 报错导致后续步骤无法执行
- 本模块内连续 3 个页面都同一个错（说明是共性问题，先停下来报告）

### 8.3 记录格式（照抄）

```markdown
### MAOPAO-007 【阻塞】【<模块名>】<列表名> → 「导出」按钮报 500

| 项 | 内容 |
| --- | --- |
| 模块 | <模块名>（系统菜单：<顶级菜单> / <二级菜单>） |
| 页面 | <顶级菜单> / <二级菜单> → `/<路由>?tab=<页签>` |
| 区域 | 页签「<页签>」下的列表工具栏 |
| 对象 | 按钮「导出」（`.toolbar button:nth-child(3)`，文字=导出） |
| 需求原文依据 | `<需求文档名>.docx` §<章节号>：**"<原文逐字引用>"** |
| 与需求不符点 | 需求要求**导出可用**，实际接口 500 —— 差在**导出分支**（不是按钮没显示，是点了必失败） |
| 操作 | 进入页签后不设任何查询条件，直接点「导出」 |
| 现象 | 页面 toast：`导出失败：系统异常`；接口 `POST /api/drug/product/export` 返回 **500**，响应体 `{"code":500,"msg":"NullPointerException"}` |
| 证据 | 截图 `data\冒泡测试-20260921\MAOPAO-007.png`；接口报文 `data\冒泡测试-20260921\api-MAOPAO-007.json`；console 无报错 |
| 依据通道 | 现象=DOM+接口报文；需求依据=需求文档原文（已解密抽正文） |
| 影响 | **阻塞**：导出功能不可用；不影响列表查询 |
| 复现 | 必现，复测 2 次均 500 |
| 时间 | 2026-09-21 13:42 |
```

**复现步骤要单独写成可照做的三行**（放在该缺陷小节里，别混进上面表格）：

```markdown
**复现步骤**
1. 打开 <顶级菜单> / <二级菜单> → `/<路由>?tab=<页签>`
2. 切到页签「<页签>」，**不填任何查询条件**
3. 点工具栏「导出」→ 观察 toast 与 `/drug/product/export` 请求
```

### 8.4 采集证据的动作顺序（现场只有一次，别丢）

1. **先截图**：`browser_take_screenshot`（失败现场，含 toast/报错弹窗）
2. **抓接口**：`browser_network_requests` 找到那条请求 → `browser_network_request` 取请求头/体 + 响应头/体
3. **抓 console**：`browser_console_messages level=error`
4. **再继续**下一步（阻塞类除外）

## §9 第八步：报告落位（**一个模块一份，不合并**）

| 产物 | 落位 |
| --- | --- |
| **本模块冒泡测试报告** | `<模块>\report\冒泡测试-<模块>-<yyyyMMdd>[-批次N].md` |
| 截图 / 接口报文 / 遍历清单 / SQL 结果 | `<模块>\data\冒泡测试-<yyyyMMdd>\` |

- **一轮测了 N 个模块 → 出 N 份报告**，各自落自己的模块；**不要合成一份总报告**。
- 跨模块的共性问题：写在**每个受影响模块**的报告里（各写一份，按本模块的现象描述），不要单独建全局报告。
- **报告结构（2026-10-13 改版：结论先行 + 缺陷速览表在最前，别让人翻半天）**：

```markdown
# <模块> 冒泡测试报告 — <环境> — <yyyyMMdd>

## 元信息（环境 / 版本 / 账号 / 测试时间 / 依据文档与版本）
## 一、结论（3~5 行说清：覆盖多少、缺陷几条、阻塞几条、能不能继续、能不能上线）
## 二、缺陷速览表 ← **必须在这里，一眼看完**
   | # | 一句话结论 | 严重 | 需求依据 | 状态 |
   例：| 1 | <列表名>「导出」必 500，导不出文件 | 阻塞 | <需求文档> §<章节> | 待修 |
## 三、缺陷详情（一条一小节，每条 ≤ 20 行、字段固定、含需求原文依据 + 与需求不符点 + 复现步骤 1./2./3.）
## 四、执行结果（覆盖情况：| 页面 | 已测 | 未覆盖 | 说明 |，未覆盖必须写原因）
## 五、对账证据（接口清单 / 数据核对 SQL；长报文与日志**只写路径**）
## 六、风险与待确认
## 七、我改过什么、是否已还原
```

> 🔴 **七条硬要求**（违反任何一条这份报告就要重写）：① 结论与**缺陷速览表**放最前；
> ② 一条缺陷一小节、**每条 ≤ 20 行**；③ 复现步骤 `1. 2. 3.` 每步一行、能照着做；
> ④ 每条缺陷**必须**有「需求原文依据」（文档名 + 章节号 + 原文引用）与「与需求不符点」；
> ⑤ 需求确实没写的写 `需求未明确`，**不许拿猜测当依据、也不许因此省略这两项**；
> ⑥ 大段日志 / 接口报文 / SQL 结果**不进正文**，落 `data\` 只写路径；
> ⑦ 写清**依据通道**（DOM / 接口报文 / SQL / 截图）。
> 完整模板见 `_templates\测试报告模板.md`；本模块的报告同样适用 `AGENTS.md` 铁律 4。

## §10 进度管理（一个模块通常一轮跑不完）

- **总是**先建遍历清单（§3.4），再开始点。
- 每完成一个节点就更新清单状态；**不要把状态只记在脑子里**（会话一断就没了）。
- 被阻塞时：记下阻塞点、跳过该节点继续测本模块其它页面（除非是共性问题，那要停下来报告）。
- 本次会话结束时：报告里写清"本模块覆盖 X/Y 页面、下一次从哪个节点续测"。
- 续测时**先读清单文件**，从第一个非 `done` 节点开始。

## §11 报告回收（满 24 小时自动进 `_archive\报告归档\`）

**规则**（2026-10-13 放宽口径，按用户要求"报告超过 24 小时自动清除掉"）：
模块 `report\` 下的**报告**、以及 `data\` 下对应的证据目录，**生成满 24 小时**后自动移到：

```
_archive\报告归档\<模块>\<yyyyMMdd>\
```

| 搬什么 | 从哪 |
| --- | --- |
| `*.md` 报告 | `<模块>\report\` |
| 证据目录 | `<模块>\data\冒泡测试-<日期>\`、`<模块>\data\需求测试-<日期>\` |

**谁会被搬 / 谁安全**（判定只看文件名，**不看内容**）：

| 文件名特征 | 结论 |
| --- | --- |
| 以 `_` 开头 | **常驻文档，永不搬**（如 `_报告模板.md`） |
| 含 **8 位日期**（`20261012`） | 归档 |
| 以 `冒泡测试-` 开头 | 归档 |
| 其它（没有日期、也不叫冒泡测试） | **常驻文档，不搬** —— 如 `增量包_新增数据明细.md` |

> 想连常驻文档一起搬：加 `--all`。想先看会动什么：加 `--dry-run`（**会逐条打印跳过原因**）。

**机制**：Windows 计划任务每小时跑一次 `archive_reports.py`（判定依据是文件修改时间，超过 24 小时即归档）。
> 这个计划任务**插件不会自动创建**，需要你自己建（见 `AGENTS.md` §六）；没建也不影响使用 —— 手动跑或走插件工具一样能归档。日志：`_archive\报告归档\_archive.log`。
⚠️ 任务名里的"冒泡测试"是**旧名**（现口径已放宽到全部报告），任务本身照跑不误。

**覆盖范围**：**框架根下所有产品**（`<产品A>\`、`<产品B>\` …）——
脚本按"框架根下非 `_` / `.` 开头、且不是 `skills\` 的目录"识别产品。
（早期版本只会扫到第一个产品，导致其它产品的报告永远不会被归档 —— 已修。）

**归档索引（2026-09-23 新增）**：模块 `SKILL.md` 里的报告/证据路径是**静态**的，
搬走后必然失效。所以每次归档会顺手回写两处：
① `<模块>\SKILL.md` 末尾的「## 归档索引」段（**只追加，绝不覆盖**既有内容，铁律 9）；
② `_archive\报告归档\<模块>\_归档索引.md` 台账。
—— 翻历史时**先看这两处**，不要凭模块 `SKILL.md` 里的静态清单去找文件。

> 跨产品**同名模块**会让归档目录撞车，脚本这时会用 `<产品>__<模块>` 并打警告。

> ⚠️ **部分机器上**应用策略会禁止运行 `pythonw.exe` 与 `wscript.exe`
> （错误 `786 = ERROR_ACCESS_DISABLED_BY_POLICY`），所以计划任务只能用 `python.exe`
> —— 每次执行会有**极短的命令行窗口一闪**，属正常现象。若想彻底无窗口，只能把任务改成
> "不管用户是否登录都要运行"（需要提供 Windows 账户密码）。

**手动跑**（想立刻回收 / 想先看会动哪些文件）：

```powershell
cd <你的框架根>\<产品>\_冒泡测试
python archive_reports.py --dry-run         # 只看会动什么（含跳过原因），不实际移动
python archive_reports.py                   # 真正归档
python archive_reports.py --hours 48        # 换时限（默认 24 小时）
python archive_reports.py --all             # 连"常驻文档"也一起搬
python archive_reports.py --backfill-index  # 按归档区现有内容补写索引，不搬文件
```

AI 侧也可以走插件工具 **`test_framework_report_gc`**（**默认 `dryRun:true`，只预演**，
确认无误再传 `dryRun:false`）（装成插件的用户）或用 CLI `dsh-test-framework report-gc` ——
它们**不重写归档逻辑，只是去找并调用上面这个 python 脚本**，所以两边规则永远一致。

**注意**：
- 归档**只搬报告与证据目录**，模块里的代码/整理稿（`final\`、`scripts\`、`requirement\`）**一律不动**。
- 归档后模块的 `report\` 只保留最近 24 小时的报告 —— 这是有意设计，让模块目录始终是"当前待跟进"的状态。
- 要翻历史：`_archive\报告归档\<模块>\`；归档区确认无用可以整体删除（但**先看 §六 的"不能删"清单**）。

## §12 快速执行清单（照着跑）

```
□ 0. 定工具：用户要「看着操作流程」→ **playwright MCP 有头浏览器 + 真实点击**（铁律 10，不许用只读 DOM/只抓报文代替）
□ 1. 问用户：环境地址 / 账号密码 / 数据库地址 / 本次测哪个模块 / 破坏性按钮策略 / 时间窗
□ 2. 预检：页面→版本→登录→权限→模块对应菜单→接口→数据库→基线快照（不通过就停）
□ 3. 枚举本模块菜单树→页面清单；逐页枚举 tab/列表/按钮/接口；落
      <模块>\data\冒泡测试-<日期>\遍历清单.json
□ 4. 逐页执行（playwright 真实操作）：打开→console→tab→列表(分页/排序/查询/重置/导出/空态)→接口核对→按钮
□ 5. CRUD：查/增(含校验与重复提交)/改(含回显)/删 —— 只用自造数据，全部打标
□ 6. 数据库核对：列表↔表、详情↔行、操作↔变化，附 SQL
□ 7. 每条报错/阻塞按 §8.3 格式记录（截图+接口报文+console）
□ 8. 出报告：<模块>\report\冒泡测试-<模块>-<日期>.md；证据落 <模块>\data\冒泡测试-<日期>\
      —— 多模块各出一份，不合并
□ 9. 收尾：清理自造数据 → 核对行数回基线 → 写"是否已还原"与"未覆盖清单"
□ 10. 报告与证据满 24h 由计划任务自动回收（也可手动 python archive_reports.py；先 --dry-run 看一遍）
```
